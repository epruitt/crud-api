# User CRUD API (AWS CDK)

A serverless user-management REST API provisioned entirely with the AWS CDK (TypeScript). An API Gateway HTTP API routes requests to a single Node.js Lambda function, which reads and writes user records in a DynamoDB table.

## Architecture Overview

This is a CDK application that provisions a user CRUD HTTP API backed by a DynamoDB table. The workflow is HTTP request → API Gateway route → Lambda handler → DynamoDB operation → HTTP response. The handler supports listing and creating users at /users, and reading, updating, and deleting users by ID. The CDK entry point creates the storage and API stacks and establishes their dependency.

The infrastructure is split into two CDK stacks:

| Stack | Defined in | Resources |
|-------|------------|-----------|
| `DynamodbStack` | `lib/dynamoddb-stack.ts` | DynamoDB table (partition key `id`, on-demand billing) |
| `CrudApiStack` | `lib/crud-api-stack.ts` | Lambda function (`NodejsFunction`), HTTP API with CORS, five routes, `HttpApiUrl` output |

`CrudApiStack` depends on `DynamodbStack`. The table name is passed to the Lambda through the `TABLE_NAME` environment variable, and the Lambda is granted read/write access to the table through the CDK's `grantReadWriteData`.

## Tech stack

- **IaC:** AWS CDK v2 (TypeScript)
- **Compute:** AWS Lambda (Node.js 24.x), bundled with esbuild via `NodejsFunction`
- **API:** Amazon API Gateway HTTP API
- **Database:** Amazon DynamoDB (AWS SDK v3, `DynamoDBDocumentClient`)
- **Testing:** Jest with SWC

## Design decisions

| Decision | Why |
|----------|-----|
| **Serverless architecture** (API Gateway + Lambda + DynamoDB) | No servers to patch or scale, and cost is near zero when idle. A good fit for a small, spiky CRUD workload. |
| **HTTP API instead of REST API** | HTTP APIs are cheaper and lower latency than REST APIs. This project doesn't need REST-only features such as API keys, usage plans, or request validation models. |
| **Two stacks: data and compute** | The stateful resource (DynamoDB) is separated from the stateless ones (Lambda, API). The API can be redeployed or destroyed without touching the table's lifecycle. `CrudApiStack` declares an explicit dependency so deployment order is correct. |
| **Cross-stack reference through props** | The table is passed to `CrudApiStack` as a typed prop (`dynamodbStack.usersTable`) instead of a hardcoded name or ARN. CDK resolves the reference, so nothing is duplicated or can drift. |
| **Single Lambda handling all routes** | One function with internal routing on method and path keeps the code in one place and means one deployment artifact and one set of logs. Routes are still declared individually in API Gateway, so the function could be split later. |
| **Routes defined as a data array** | The five routes are listed once and registered in a loop, which avoids repeating the integration boilerplate and makes adding a route a one-line change. |
| **`NodejsFunction` (esbuild bundling)** | TypeScript is bundled and tree-shaken at synth time, so there's no separate build or packaging step for the Lambda. |
| **DynamoDB on-demand billing** | There's no capacity planning, and there's no cost when the API isn't used. |
| **Partition key `id` as a server-generated UUID v4** | Gives even key distribution, makes `GetItem`, `UpdateItem`, and `DeleteItem` single-key lookups, and keeps clients from choosing their own IDs. |
| **`createdAt` set by the server** | Timestamps come from the API, not the client, so they can be trusted. |
| **AWS SDK v3 `DynamoDBDocumentClient`** | Works with plain JavaScript objects and avoids manual attribute-value marshalling. The v3 client is modular, which keeps the bundle small. |
| **Table name passed as an environment variable** | The handler isn't coupled to a hardcoded name, and the name follows the stack (`<stack>-users-table`). |
| **`grantReadWriteData` for IAM** | CDK generates a scoped policy limited to this one table, instead of a hand-written or wildcard policy. |
| **`RemovalPolicy.DESTROY` on the table** | Makes `cdk destroy` clean up completely during development. It's flagged in the code as not suitable for production. |
| **Open CORS (`*`)** | Lets any front end or test client call the API during development. It should be restricted before real use. |
| **Prefixing resource names with the stack name** | The Lambda and table names are derived from `stackName`, so multiple copies of the stack can be deployed side by side without name collisions. |
| **`tsx` to run the CDK app, Jest with SWC** | Fast TypeScript execution and test runs without a heavier compile step. |
| **Accept `name` and `email` from the request body** | An earlier version of the handler generated fake users with Faker (still visible as commented-out code). The API now takes real input from the caller. |

## Prerequisites

- Node.js 20+ and npm
- An AWS account with credentials configured (`aws configure` or environment variables)
- The AWS CDK CLI (installed locally through `npx cdk`)
- The target account/region [bootstrapped](https://docs.aws.amazon.com/cdk/v2/guide/bootstrapping.html) once:

  ```bash
  npx cdk bootstrap
  ```

## Getting started

```bash
# Clone and install
git clone https://github.com/epruitt/crud-api.git
cd crud-api
npm install

# Preview what will be created
npx cdk synth
npx cdk diff

# Deploy both stacks
npx cdk deploy --all
```

When deployment finishes, the HTTP API URL is printed as the `HttpApiUrl` output of `CrudApiStack`. Use it as the base URL for the requests below.

## API reference

Base URL: the `HttpApiUrl` stack output.

| Method | Path | Description | Success |
|--------|------|-------------|---------|
| `GET` | `/users` | List all users | `200` |
| `POST` | `/users` | Create a user | `201` |
| `GET` | `/users/{id}` | Get a user by ID | `200` |
| `PUT` | `/users/{id}` | Update a user's name and email | `200` |
| `DELETE` | `/users/{id}` | Delete a user | `200` |

### User object

```json
{
  "id": "b2f1c5de-0c0a-4a39-9d57-3a1f6f0f6e11",
  "name": "John Jones",
  "email": "john.jones@example.com",
  "createdAt": "2026-01-01T12:00:00.000Z"
}
```

`id` (UUID v4) and `createdAt` (ISO 8601) are generated by the server.

### Examples

**Create a user**

```bash
curl -X POST "$API_URL/users" \
  -H "Content-Type: application/json" \
  -d '{"name": "John Jones", "email": "john.jones@example.com"}'
```

**List users**

```bash
curl "$API_URL/users"
```

**Get a user**

```bash
curl "$API_URL/users/<id>"
```

**Update a user**

```bash
curl -X PUT "$API_URL/users/<id>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Jane Jones", "email": "jane.jones@example.com"}'
```

**Delete a user**

```bash
curl -X DELETE "$API_URL/users/<id>"
```

A ready-made set of requests is also available in [`test/makeRequests.http`](test/makeRequests.http) for use with the VS Code [REST Client](https://marketplace.visualstudio.com/items?itemName=humao.rest-client) extension. Update the `@URL` variable at the top with your own API URL.

### Error responses

| Status | Meaning |
|--------|---------|
| `400` | Unsupported HTTP method, or missing user ID |
| `404` | Route not found, or user not found (`GET /users/{id}`) |
| `500` | Unhandled server error (details are logged to CloudWatch) |

## Cleanup

To avoid ongoing charges, remove the resources when you're done:

```bash
npx cdk destroy --all
```

The DynamoDB table uses `RemovalPolicy.DESTROY`, so **its data is deleted along with the stack**.

## Known limitations and next steps

This project is a learning/demo build. Before using something like it in production, consider:

- **No authentication.** The API is public and CORS allows all origins (`*`). Add an authorizer (e.g., JWT/Cognito or IAM) and restrict origins.
- **No input validation.** Request bodies are not validated, so malformed JSON returns a `500`. Add schema validation (e.g., Zod) and return `400`.
- **`GET /users` uses a DynamoDB `Scan`**, which is not paginated and gets expensive as the table grows.
- **`PUT` and `DELETE` don't check existence.** Updating or deleting an unknown ID does not return `404`.
- **Table removal policy is `DESTROY`.** Switch to `RETAIN` and enable point-in-time recovery for real data.
- **Tests are placeholders.** Add CDK assertion tests for the stacks and unit tests for the handler.
- **Single Lambda for all routes.** Fine at this size; consider splitting per route as the API grows.
